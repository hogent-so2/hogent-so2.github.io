MAUI – MVVM & CollectionView

In de vorige les hebben we Inversion of Control, Dependency Injection en onze JokeService uitgewerkt. Vanaf deze les schakelen we over naar MVVM, de standaardarchitectuur voor MAUI-apps.

We gebruiken dezelfde oefening (de Joke-app) om MVVM stap voor stap te introduceren. Zo groeit de app les na les mee, zonder dat we telkens helemaal opnieuw beginnen.

MVVM

MVVM is een architecturaal patroon dat staat voor Model – View – ViewModel. Het wordt veel gebruikt in frameworks zoals MAUI, WPF, Xamarin, Avalonia, enz. Het doel is om UI en logica strikt te scheiden, zodat applicaties overzichtelijker, testbaar en uitbreidbaar worden.

Model

Data en domeinlogica, de BL. Het model kent de UI niet.

View

De UI, dus de XAML-pagina’s en hun views. Deze toont de gegevens van het ViewModel. Bevat geen logica behalve UI-logica (animaties, opmaak, simpele event-afhandeling die puur visueel is).

ViewModel

De brug tussen Model en View. Het ViewModel haalt of bewaart data via services of repositories. Deze stelt properties en commands beschikbaar voor de View via binding. Het ViewModel kent de view niet rechtstreeks, enkel via binding.

Belangrijke principes:

  • De View kent het ViewModel via BindingContext.

  • Het ViewModel kent de View niet.

  • Modellen kennen noch View, noch ViewModel.

Concreet: onze Joke-app in MVVM

We gebruiken het Joke-model al sinds de eerste MAUI-les. Het model hoeft voor MVVM niet te veranderen. De data van het model wordt gebruikt om ViewModels op te bouwen. Deze ViewModels stellen via hun eigen properties precies de informatie ter beschikking die de UI nodig heeft.

Deze ViewModels zijn dus ook wel terug models, maar voor de view: vandaar de naam viewMODEL. De eigenschappen van de ViewModels kunnen gelijklopen met de eigenschappen van het model, maar dit hoeft niet. Hiermee bedoelen we dat als je model een eigenschap Naam heeft, dan zal je ViewModel dit waarschijnlijk ook hebben. Het kan zijn dat je model een eigenschap Geboortedatum heeft en in je ViewModel kan dit bv. eerder de berekende waarde Leeftijd zijn.

De UI zal zich binden aan een ViewModel. Binnen MAUI kan je dit doen via Binding.

We vertrekken van de Joke-app uit de vorige les, waar de logica grotendeels in code-behind stond.

Data binding

Data binding is het mechanisme waarmee de UI (XAML) automatisch verbonden wordt met properties in het ViewModel.

De View leest dus niet meer rechtstreeks uit C#-code-behind, maar uit het ViewModel.

Dit zorgt ervoor dat de UI automatisch verandert wanneer het ViewModel verandert en dat het ViewModel verandert wanneer de gebruiker in de UI iets aanpast.

Stel dat je een ViewModel JokeListViewModel hebt, dan stel je in de view de BindingContext in:

public partial class JokeListPage : ContentPage
{
    public JokeListPage(JokeListViewModel vm)
    {
        InitializeComponent();

        BindingContext = vm;
    }
}

En in XAML bind je:

<ContentPage xmlns="http://schemas.microsoft.com/dotnet/2021/maui"
             x:Class="JokeApp.Views.JokeListPage">
    <VerticalStackLayout Padding="20">
        <Label Text="{Binding CurrentJoke}" />
    </VerticalStackLayout>
</ContentPage>

Hier wordt Text automatisch geüpdatet wanneer CurrentJoke wijzigt, op voorwaarde dat het ViewModel INotifyPropertyChanged correct implementeert. Op INotifyPropertyChanged komen we later nog terug.

Command binding

In plaats van click-events in code-behind gebruiken we commands in het ViewModel via de interface ICommand.

De ViewModel wordt iets zoals:

public class JokeListViewModel : INotifyPropertyChanged
{
    public event PropertyChangedEventHandler PropertyChanged;

    private readonly IJokeService _jokeService;

    public ICommand NewJokeCommand { get; }

    public JokeListViewModel(IJokeService jokeService)
    {
        _jokeService = jokeService;

        NewJokeCommand = new Command(() => OnNewJoke());
    }

    private void OnNewJoke()
    {
        ...
    }
}

En in de XAML gebruiken we dan de Command eigenschap op bv. een button:

<Button Text="Nieuwe grap"
        Command="{Binding NewJokeCommand}" />

De knop roept nu de command aan in het ViewModel, zonder dat we een event handler in de code-behind nodig hebben.

Voordelen:

  • Minder code-behind

  • Makkelijker te testen

  • Duidelijke scheiding tussen UI en logica

INotifyPropertyChanged

INotifyPropertyChanged is een interface die aangeeft dat een object kan laten weten wanneer één van zijn properties verandert.

Het is een kernonderdeel van MVVM:Zonder INotifyPropertyChanged wordt de UI niet automatisch vernieuwd wanneer een property na de initiële binding wijzigt. Databinding betekent dat de UI (bijv. een Label of Entry) automatisch geüpdatet wordt wanneer de onderliggende property in het ViewModel wijzigt. MAUI moet dus weten wanneer een property veranderd is.

Dat 'ik ben gewijzigd' signaal wordt gegeven door INotifyPropertyChanged.

INotifyPropertyChanged bevat maar één eigenschap:

public event PropertyChangedEventHandler PropertyChanged;

Als een property verandert, moet je zelf het bijhorende event activeren. Dit gebeurt door alle subscribers van het event aan te roepen:

PropertyChanged?.Invoke(this, new PropertyChangedEventArgs(nameof(CurrentJoke)));

De UI luistert naar deze events en weet dan:

"Ah, de property CurrentJoke is veranderd, ik moet de UI updaten."

Een volledige bindbare property ziet er concreet zo uit:

public class JokeListViewModel : INotifyPropertyChanged
{
    public event PropertyChangedEventHandler PropertyChanged;

    private string _currentJoke = string.Empty;
    public string CurrentJoke
    {
        get => _currentJoke;
        set
        {
            if (_currentJoke == value) return;
            _currentJoke = value;
            PropertyChanged?.Invoke(this, new PropertyChangedEventArgs(nameof(CurrentJoke)));
        }
    }
}

De check if (_currentJoke == value) return; voorkomt dat het event onnodig afgevuurd wordt wanneer de waarde niet veranderd is.

CollectionView

CollectionView is de control in MAUI om lijsten efficiënt te tonen.

Belangrijkste eigenschappen:

  • ItemsSource: de ViewModel collectie

  • ItemTemplate: de template die gebruikt wordt om de view op te bouwen voor de items van de collectie

  • SelectionMode: wat voor selectie is mogelijk

  • SelectedItem: het geselecteerde item

Voorbeeld XAML:

<CollectionView ItemsSource="{Binding Jokes}"
                SelectionMode="Single"
                SelectedItem="{Binding SelectedJoke}">
    <CollectionView.ItemTemplate>
        <DataTemplate>
            <Border Padding="10" Margin="4">
                <Label Text="{Binding Text}" />
            </Border>
        </DataTemplate>
    </CollectionView.ItemTemplate>
</CollectionView>
Voor de DataTemplate wordt het item (één JokeViewModel) als BindingContext gezet. De Label binnen de DataTemplate heeft dus niet de pagina-ViewModel als BindingContext, maar 1 enkele JokeViewModel.

Item-ViewModel:

public class JokeViewModel
{
    public Guid Id { get; }
    public string Text { get; }
    public string Category { get; }

    public JokeViewModel(Joke joke)
    {
        Id = joke.Id;
        Text = joke.Text;
        Category = joke.Category.ToString();
    }
}
Een GUID is een Globally Unique Identifier, een 128-bit waarde die vrijwel gegarandeerd uniek is.

We gebruiken hier een JokeViewModel in plaats van de domeinklasse Joke rechtstreeks. Dit scherm heeft mogelijk niet alle properties van Joke nodig, of wil ze anders presenteren — bv. een afgekorte tekst of een berekende waarde. Door een apart item-ViewModel te maken, blijft de domeinklasse ongewijzigd en bevat de UI-klasse precies wat ze nodig heeft.

ObservableCollection<T>

Wanneer de lijst in het ViewModel kan veranderen (items toevoegen, verwijderen, enz.), gebruik je ObservableCollection.

ViewModel:

public class JokeListViewModel : INotifyPropertyChanged
{
    ...

    public ObservableCollection<JokeViewModel> Jokes { get; };

    ...

    public JokeListViewModel(IJokeService jokeService)
    {
        var jokes = jokeService.GetAll()
                               .Select(joke => new JokeViewModel(joke));
        Jokes = new ObservableCollection<JokeViewModel>(jokes);
    }

    ...
}

XAML:

<CollectionView ItemsSource="{Binding Jokes}">
    <CollectionView.ItemTemplate>
        <DataTemplate>
            <Border Padding="10" Margin="4">
                <Label Text="{Binding Text}" />
            </Border>
        </DataTemplate>
    </CollectionView.ItemTemplate>
</CollectionView>

Omdat we ObservableCollection gebruiken, wordt de CollectionView automatisch geüpdatet zonder extra code.

Repository en data-opslag met LiteDB

Tot nu toe bewaarden we de grappen in het geheugen. We kunnen hetzelfde DI-principe toepassen voor echte data-opslag, via een repository en een database zoals LiteDB.

LiteDB is een eenvoudige NoSQL-database in één enkel bestand. Je kan er rechtstreeks C#-objecten in bewaren zonder tabellen of SQL te definiëren.

LiteDB-implementatie van de repository

Je voegt ondersteuning toe voor LiteDB via NuGet in je project.

using LiteDB;

public class LiteDBJokeRepository : IJokeRepository, IDisposable
{
    private const string DatabaseFileName = "joke_db.db";

    private readonly LiteDatabase _database;

    // Een collection is vergelijkbaar met een tabel in een relationele databank.
    private ILiteCollection<Joke> JokeCollection
        => _database.GetCollection<Joke>();

    public LiteDBJokeRepository()
    {
        var databasePath = Path.Combine(
            FileSystem.AppDataDirectory,
            DatabaseFileName);

        _database = new LiteDatabase(databasePath);
    }

    public void Add(Joke joke)
        => JokeCollection.Insert(joke);

    public Joke? GetById(Guid id)
        => JokeCollection.FindById(id);

    public IReadOnlyList<Joke> GetAll()
        => JokeCollection.FindAll().ToList().AsReadOnly();

    public void Remove(Guid id)
        => JokeCollection.Delete(id);

    public void Dispose()
    {
        _database.Dispose();
    }
}

Registratie in MauiProgram

// Singleton omdat we willen vermijden dat we meerdere connecties openen naar LiteDB
builder.Services.AddSingleton<IJokeRepository, LiteDBJokeRepository>();

builder.Services.AddTransient<IJokeService, JokeService>();

Voor de ViewModel en de pagina verandert er niets: die werken nog altijd via IJokeService, onbewust van LiteDB.

Oefening

Vertrek van de Joke-app uit de vorige les en breng de bestaande schermen over naar MVVM. De zichtbare werking en de globale styles blijven behouden.

Must

  • Maak een JokeListViewModel voor het overzicht en een ViewModel voor het toevoegscherm.

  • Vervang Clicked-handlers voor applicatieacties door commands.

  • Bind invoer, validatieboodschap en knoptoestand aan properties van het ViewModel.

  • Toon de grappen via een ObservableCollection<JokeViewModel> in de bestaande CollectionView.

  • Laat ieder item maximaal twee lijnen tekst tonen met MaxLines.

  • Registreer ViewModels en pagina’s via de DI-container.

  • Vervang de in-memory repository door een LiteDBJokeRepository. De pagina’s en ViewModels mogen daardoor niet wijzigen.

Should

  • Vertaal verwachte model- en service-exceptions naar een bindbare validatieboodschap.

  • Maak de toevoegcommand alleen uitvoerbaar wanneer er potentieel geldige invoer aanwezig is.

  • Toon de volledig geselecteerde grap in een afzonderlijk detailvlak.

Could

  • Maak een herbruikbare BaseViewModel die INotifyPropertyChanged implementeert.

  • Voeg een filter op categorie toe zonder filtering in de View te plaatsen.

  • Schrijf een unit test voor minstens één command in een ViewModel.
