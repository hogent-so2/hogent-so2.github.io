MAUI - Details, bewerken & messaging

Startcode nodig? Je vindt de code van vorige les op Github. Heb je zelf een werkende vorige versie, dan is het sterk aangeraden om daarin verder te werken.

We werken onze JokeApp verder af. Vanuit het overzicht openen we een bestaande grap, passen haar aan en bewaren of annuleren de wijziging. Daarna laten we onderdelen via een bericht weten dat de verzameling gewijzigd is.

WebAPI staat verderop als facultatieve preview op andere lessen. De preview is uitgewerkt als sluitstuk van onze app, maar is geen verplicht onderdeel en wordt alleen behandeld als er tijd over is. Details, bewerken en messaging vormen de kern; een internetverbinding is daarvoor niet nodig.

Vertrekpunt: één app en één bron van gegevens

Behoud alle models, validatieregels, repositories, services, styles en ViewModels. MainPage blijft het overzicht. De thuisopdracht voegde een verwijdercommand en feedback toe; die komen ook terug in de gezamenlijke overzichtsversie verderop.

Onze ObservableCollection<Joke> is een weergave van de gegevens, geen tweede opslagplaats. Een detailscherm krijgt daarom een id en vraagt de actuele grap aan de service.

We bouwen eerst de detail- en bewerkstroom met de bestaande OnAppearing-refresh. Pas wanneer die werkt, voegen we messaging toe. Zo lossen we niet tegelijk een navigatie-, opslag- en notificatieprobleem op.

Eerst voorspellen: wat betekent Annuleren?

We willen een grap kunnen wijzigen zonder dat iedere toetsaanslag al de bewaarde grap verandert. Stel dat het invoerveld rechtstreeks aan Joke.Text gebonden is. Je typt een andere, geldige tekst en klikt daarna op Annuleren. Is het oorspronkelijke object dan nog ongewijzigd?

Onderzoek dit kort met de InMemoryJokeRepository uit de vorige les. Onderstaande tijdelijke proef hoort bij het vertrekpunt, vóór we messaging toevoegen. Ze gebruikt haar eigen repository met startgrappen en wijzigt dus niet de gegevens van je draaiende app.

var repository = new InMemoryJokeRepository();
var service = new JokeService(repository);
var original = service.GetAll()[0];
var editing = service.GetById(original.Id)!;

editing.Text = "Deze gewijzigde grap is nog niet expliciet opgeslagen.";

Voorspel eerst wat original.Text nu bevat. Controleer daarna met een breakpoint zowel de tekst als ReferenceEquals(original, editing). Die laatste controle is true: twee variabelen verwijzen naar hetzelfde object. Er is nergens Update aangeroepen, maar het object in de in-memory collectie is al gewijzigd.

Deze proef toont geen schrijfactie naar LiteDB. Ze toont dat een object wijzigen en een wijziging bewust laten bewaren verschillende handelingen zijn. We willen dat de app met beide repositories hetzelfde gedrag voor Opslaan en Annuleren aanbiedt.

Daarom maken we een onderscheid:

  • Het formulier bewaart eigen invoer die nog mag veranderen.

  • Opslaan vraagt de service om die invoer te controleren en de wijziging te bewaren.

  • Annuleren verlaat het formulier zonder die bewerking te vragen.

Bewaar geen kopie van de volledige bibliotheek in het formulier en probeer bij annuleren niet achteraf alle wijzigingen terug te draaien. Alleen tekst en categorie vormen hier de tijdelijke invoer. De oorspronkelijke grap blijft tot een geslaagde opslag onaangeroerd. Verwijder de tijdelijke proefcode voordat je verderwerkt.

Een detailroute met een id

Breid het bestaande navigatiecontract uit. De ViewModels blijven vrij van routenamen en Shell.Current.

Navigation/INavigationService.cs
namespace JokeApp.Navigation;

public interface INavigationService
{
    Task ShowAddJokeAsync();
    Task ShowJokeDetailAsync(Guid jokeId);
    Task GoBackAsync();
}
Navigation/ShellNavigationService.cs
namespace JokeApp.Navigation;

public sealed class ShellNavigationService : INavigationService
{
    public Task ShowAddJokeAsync() =>
        Shell.Current.GoToAsync(nameof(AddJokePage));

    public Task ShowJokeDetailAsync(Guid jokeId) =>
        Shell.Current.GoToAsync(
            nameof(JokeDetailPage),
            new Dictionary<string, object>
            {
                ["JokeId"] = jokeId
            });

    public Task GoBackAsync() =>
        Shell.Current.GoToAsync("..");
}

We geven geen verwijzing naar een rij of een te bewerken model door. De vraag aan het detailscherm is: open de grap met deze identiteit, niet: gebruik dit object uit mijn lijst. Met de Guid vraagt het detailscherm de grap opnieuw aan de service en kan het expliciet afhandelen dat ze niet meer bestaat.

Een id doorgeven is hier een bewuste keuze, geen algemene MVVM-verplichting. Ook een model doorgeven is technisch mogelijk. De id houdt deze navigatie onafhankelijk van de objecten die het overzicht op dat moment heeft geladen en helpt ons de formulierinvoer van het bewaarde model te scheiden.

De Task-, async- en await-syntax nemen we opnieuw over als vast recept. Deze les behandelt navigatie en verantwoordelijkheden, niet asynchroon programmeren.

Voeg in AppShell na de bestaande route deze registratie toe:

Routing.RegisterRoute(nameof(JokeDetailPage), typeof(JokeDetailPage));

Registreer vóór Build() in MauiProgram ook:

builder.Services.AddTransient<JokeDetailPage>();
builder.Services.AddTransient<JokeDetailViewModel>();

De pagina en het ViewModel maken we hieronder. Werk een eventuele testdouble van INavigationService mee bij: ook die moet de nieuwe methode aanbieden.

Bewaren is iets anders dan toevoegen

Een bestaande grap bewerken via Add zou een tweede record opleveren. Daarom breiden we het repositorycontract uit met:

bool Update(Joke joke);

Voeg deze methode toe aan InMemoryJokeRepository:

public bool Update(Joke joke)
{
    ArgumentNullException.ThrowIfNull(joke);
    var index = _jokes.FindIndex(existing => existing.Id == joke.Id);

    if (index < 0)
        return false;

    _jokes[index] = joke;
    return true;
}

Voeg de overeenkomstige implementatie toe aan LiteDbJokeRepository:

public bool Update(Joke joke)
{
    ArgumentNullException.ThrowIfNull(joke);
    return _jokes.Update(joke);
}

Beide implementaties zoeken op Id. Ze vervangen een bestaand object en melden of dat gelukt is. Ze voegen bij een onbekende id niet stilzwijgend een nieuwe grap toe.

De service bewaakt de bewerking

Voeg aan IJokeService toe:

ValidationResult Update(Guid id, string text, JokeCategory category);

En voeg deze methode toe aan JokeService:

public ValidationResult Update(Guid id, string text, JokeCategory category)
{
    var existingJoke = _jokeRepository.GetById(id);

    if (existingJoke is null)
        return ValidationResult.Failure("Deze grap bestaat niet meer.");

    var validation = JokeTextValidator.Validate(text);

    if (!validation.IsValid)
        return validation;

    var normalizedText = text.Trim();
    var duplicateExists = _jokeRepository.GetAll().Any(other =>
        other.Id != id &&
        string.Equals(other.Text, normalizedText,
            StringComparison.OrdinalIgnoreCase));

    if (duplicateExists)
        return ValidationResult.Failure("Deze grap bestaat al.");

    var updatedJoke = new Joke(normalizedText, category)
    {
        Id = existingJoke.Id
    };

    if (!_jokeRepository.Update(updatedJoke))
        return ValidationResult.Failure("Deze grap bestaat niet meer.");

    return ValidationResult.Success();
}

De uitzondering other.Id != id is essentieel. Anders zou Opslaan zonder tekstwijziging de grap als duplicaat van zichzelf weigeren.

We maken pas na de controles een vervangend model, met dezelfde id. Een nieuw C#-object is hier dus geen nieuwe grap: het vervangt de voorstelling van dezelfde grap in onze bibliotheek. init laat toe die id bij het maken mee te geven, maar niet later op het object te wijzigen.

Voorspel het verschil: wat gebeurt er als we Id = existingJoke.Id weglaten? De constructor maakt dan een nieuwe id. Onze repository vindt onder die id geen bestaande grap om bij te werken; Update meldt een mislukking. Een nieuwe objectreferentie en een nieuwe domeinidentiteit zijn niet hetzelfde.

We wijzigen het opgezochte object niet eerst om daarna te controleren of alles mag. Dat is vooral bij de in-memory repository belangrijk: die kan hetzelfde object aan meerdere gebruikers teruggeven. Bij een mislukte bewerking moet de oorspronkelijke grap intact blijven.

Waarom ontvangt Update losse formulierwaarden terwijl Add een nieuw model ontvangt? We behouden het toevoegcontract uit de vorige les: het toevoegformulier valideert en maakt daarna een nieuw model. Voor bewerken kiezen we een verzoek met een bestaande id en voorgestelde tekst en categorie. De service controleert dat verzoek en maakt pas bij geldige invoer het vervangende model.

Dat zijn ontwerpkeuzes, geen technische verplichtingen. Je kan beide servicebewerkingen ook consequent invoerwaarden laten ontvangen. Een Update die een model ontvangt is eveneens mogelijk. Het bewaken van identiteit verplicht ons op zichzelf niet tot losse parameters. In deze opbouw veranderen we het bestaande toevoegcontract niet tegelijk met de nieuwe bewerkstroom.

Belangrijker dan die parameterkeuze zijn de vaste afspraken: dezelfde tekstregels hergebruiken, duplicaten bij de service controleren en de oorspronkelijke grap intact laten bij een geweigerde wijziging.

Test deze methode eerst zonder navigatie: bewaar ongewijzigd, wijzig naar de tekst van een andere grap, gebruik een onbekende id en geef ongeldige tekst door. Controleer na iedere mislukking zowel de tekst als het aantal records.

Het detailscherm bewaart eigen formulierinvoer

We lossen nu het probleem uit de beginproef op. JokeDetailViewModel kopieert tekst en categorie naar eigen properties. TwoWay schrijft alleen naar die properties, niet rechtstreeks naar Joke.Text. Een lege formuliertekst mag dus tijdelijk bestaan zonder dat we een ongeldig model maken.

Dit maakt Annuleren eenvoudig: we keren terug zonder de service een wijziging te laten bewaren. Er hoeft niets in de database teruggedraaid te worden.

Controleer straks vóór je op Opslaan klikt: de tekst in het ViewModel mag verschillen van de tekst die GetById teruggeeft. Juist dat verschil toont dat de gebruiker nog een voorstel aan het bewerken is.

ViewModels/JokeDetailViewModel.cs
using System.Windows.Input;
using JokeApp.Models;
using JokeApp.Navigation;
using JokeApp.Services;

namespace JokeApp.ViewModels;

public sealed class JokeDetailViewModel : ViewModelBase
{
    private readonly IJokeService _jokeService;
    private readonly INavigationService _navigationService;
    private Guid _jokeId;
    private bool _isLoaded;
    private string _text = string.Empty;
    private JokeCategory _selectedCategory;
    private string _errorMessage = string.Empty;

    public IReadOnlyList<JokeCategory> Categories { get; } =
        Enum.GetValues<JokeCategory>();

    public string Text
    {
        get => _text;
        set
        {
            if (SetProperty(ref _text, value))
                ErrorMessage = string.Empty;
        }
    }

    public JokeCategory SelectedCategory
    {
        get => _selectedCategory;
        set => SetProperty(ref _selectedCategory, value);
    }

    public string ErrorMessage
    {
        get => _errorMessage;
        private set
        {
            if (SetProperty(ref _errorMessage, value))
                OnPropertyChanged(nameof(HasError));
        }
    }

    public bool HasError => ErrorMessage.Length > 0;

    public bool IsLoaded
    {
        get => _isLoaded;
        private set
        {
            if (SetProperty(ref _isLoaded, value))
            {
                SaveCommand.ChangeCanExecute();
                DeleteCommand.ChangeCanExecute();
            }
        }
    }

    public Command SaveCommand { get; }
    public Command DeleteCommand { get; }
    public ICommand CancelCommand { get; }

    public JokeDetailViewModel(
        IJokeService jokeService,
        INavigationService navigationService)
    {
        _jokeService = jokeService;
        _navigationService = navigationService;
        SaveCommand = new Command(async () => await SaveAsync(), () => IsLoaded);
        DeleteCommand = new Command(async () => await DeleteAsync(), () => IsLoaded);
        CancelCommand = new Command(async () => await navigationService.GoBackAsync());
    }

    public void Load(Guid jokeId)
    {
        IsLoaded = false;
        _jokeId = jokeId;
        Text = string.Empty;
        ErrorMessage = string.Empty;

        var joke = _jokeService.GetById(jokeId);

        if (joke is null)
        {
            ErrorMessage = "Deze grap bestaat niet meer.";
            return;
        }

        Text = joke.Text;
        SelectedCategory = joke.Category;
        IsLoaded = true;
    }

    private async Task SaveAsync()
    {
        ErrorMessage = string.Empty;
        var result = _jokeService.Update(_jokeId, Text, SelectedCategory);

        if (!result.IsValid)
        {
            ErrorMessage = result.ErrorMessage;
            return;
        }

        await _navigationService.GoBackAsync();
    }

    private async Task DeleteAsync()
    {
        ErrorMessage = string.Empty;
        var result = _jokeService.Remove(_jokeId);

        if (!result.IsValid)
        {
            ErrorMessage = result.ErrorMessage;
            return;
        }

        await _navigationService.GoBackAsync();
    }
}

IsLoaded bepaalt of er een bestaande grap is om te bewaren of verwijderen. Het zegt niets over de geldigheid van de ingevoerde tekst. Met een leeg tekstveld blijft Opslaan dus beschikbaar zolang er een grap geladen is.

Command is de ingebouwde MAUI-klasse. Voor deze commands installeren we geen extra package. De vorm new Command(async () ⇒ await SaveAsync(), …​) verbindt het command met het bestaande navigatierecept. Geef de Task-methode niet rechtstreeks door als new Command(SaveAsync, …​); de callbackvorm met async () ⇒ await …​ hoort bij dat recept.

Waarom bewaren we SaveCommand en DeleteCommand hier als Command, niet alleen als ICommand? De View heeft genoeg aan ICommand, maar het ViewModel moet ChangeCanExecute() kunnen aanroepen. Die hulpmethode staat op Command, niet op de interface.

ChangeCanExecute() laat de View de beschikbaarheid opnieuw opvragen. CanExecuteChanged is het event dat daarbij wordt verstuurd, geen methode die we zelf aanroepen. Een wijziging van IsLoaded wordt niet automatisch door het command opgemerkt. Zie Microsoft: commanding.

JokeDetailPage.xaml.cs
using JokeApp.ViewModels;

namespace JokeApp;

public partial class JokeDetailPage : ContentPage, IQueryAttributable
{
    private readonly JokeDetailViewModel _viewModel;

    public JokeDetailPage(JokeDetailViewModel viewModel)
    {
        InitializeComponent();
        _viewModel = viewModel;
        BindingContext = viewModel;
    }

    public void ApplyQueryAttributes(IDictionary<string, object> query)
    {
        var jokeId = query.TryGetValue("JokeId", out var value)
            && value is Guid id
                ? id
                : Guid.Empty;

        _viewModel.Load(jokeId);

IQueryAttributable is hier een MAUI-verantwoordelijkheid van de pagina. Zij vertaalt de navigatiegegevens naar een gewone Guid voor het ViewModel. Bij een ontbrekende of verkeerd getypeerde parameter levert Guid.Empty in onze app een niet-gevondenmelding op.

We laden niet opnieuw bij iedere toetsaanslag of zomaar bij elk verschijnen van de pagina. Dat zou nog niet opgeslagen formulierinvoer kunnen overschrijven.

Een command om de selectie te openen

Voeg aan JokeListViewModel een veld _navigationService toe en bewaar de ontvangen navigatieservice daarin. Voeg vervolgens toe:

public Command OpenDetailsCommand { get; }

private async Task OpenDetailsAsync()
{
    if (SelectedJoke is not null)
        await _navigationService.ShowJokeDetailAsync(SelectedJoke.Id);
}

Initialiseer in de constructor:

OpenDetailsCommand = new Command(
    async () => await OpenDetailsAsync(), () => SelectedJoke is not null);

Roep in de setter van SelectedJoke, binnen de bestaande if, ook OpenDetailsCommand.ChangeCanExecute() aan. Zonder selectie is er niets om te openen; dat is een beschikbaarheidsvoorwaarde, geen invoervalidatie.

Voeg een knop Details met Command="{Binding OpenDetailsCommand}" toe aan de actiebalk. Geef de Grid daarvoor een extra kolom. De volledige overzichtsversie verderop toont dit samen met de verwijderfunctie.

Test nu de volledige stroom terwijl MainPage.OnAppearing nog gewoon Reload oproept:

  1. Open een grap, wijzig tekst en categorie en sla op.

  2. Controleer dat het aantal gelijk blijft en de wijziging na een herstart bewaard is.

  3. Open dezelfde grap, wijzig de invoer en annuleer. Het origineel blijft intact.

  4. Sla een grap ongewijzigd op: dit moet lukken.

  5. Probeer de tekst van een andere grap en controleer dat de oude tekst behouden blijft.

  6. Bewerk een grap zodat ze niet meer aan de actieve zoekopdracht voldoet. Ze verdwijnt uit de resultaten, niet uit de opslag.

Wanneer is messaging nuttig?

Tot nu toe vernieuwt het overzicht wanneer het opnieuw verschijnt. Dat is voor deze kleine app een goede, eenvoudige oplossing. Ze koppelt het detailscherm ook niet rechtstreeks aan het overzicht. We vervangen haar niet omdat ze fout is.

Een nieuwe behoefte: twee presentaties bijwerken

We willen naast de zoekresultaten een klein statistiekpaneel tonen met aantallen per categorie. De lijst toont bijvoorbeeld alleen grappen met koffie; het paneel blijft de volledige bibliotheek tellen. Beide presentaties hebben dus hun eigen toestand.

Voorspel wat moet gebeuren wanneer een grap van Programming naar Other verhuist en haar tekst niet meer bij de zoekopdracht past. De lijst moet een rij weglaten, het totale aantal grappen blijft gelijk en twee categorietellers veranderen. Later kan ook een ander scherm belangstelling hebben voor die wijziging.

Wie moet nu weten welke onderdelen moeten reageren? Bespreek eerst de mogelijkheden:

  • Het detailscherm kan elk ander onderdeel expliciet laten verversen. Dan moet iedere invoerroute al die ontvangers kennen.

  • De pagina kan bij terugkeer beide presentaties opnieuw laden. Dat blijft een bruikbare eenvoudige keuze als vernieuwen op dat moment volstaat.

  • De service kan melden dat de gegevens gewijzigd zijn. Elk geïnteresseerd onderdeel bepaalt dan zelf wat het moet bijwerken.

We onderzoeken de derde mogelijkheid. Het doel is dat een nieuwe ontvanger kan aansluiten zonder dat de afzender alle schermen hoeft op te sommen.

We hebben toch al wijzigingsmeldingen?

Uit de vorige les kennen we twee soorten meldingen. Die hebben niet dezelfde rol als ons nieuwe bericht:

PropertyChanged

Een propertywaarde is gewijzigd. Een binding kan bijvoorbeeld CountText opnieuw lezen en een label bijwerken.

CollectionChanged van ObservableCollection

Items zijn in die collectie toegevoegd, verwijderd of vervangen. De CollectionView kan haar rijen aanpassen.

JokesChangedMessage

Een bewerking op de opgeslagen grappen is geslaagd. Geïnteresseerde ViewModels bepalen welke gegevens ze opnieuw moeten lezen.

Een wijziging in LiteDB roept geen Jokes.Add op en berekent geen nieuwe categorietellers. Ook het vervangen van een object in de in-memory repository wijzigt niet vanzelf een eerder gevulde ObservableCollection. Dat blijft een afzonderlijke weergave.

Het nieuwe bericht vervangt binding dus niet. Het laat een ViewModel reageren op gewijzigde gegevens. Dat ViewModel werkt vervolgens zijn properties of collectie bij; hun meldingen zorgen dat de UI mee verandert.

Wat winnen we, en wat kost het?

In deze les gebruiken we een command als verzoek om iets te doen en een wijzigingsbericht als melding van een feit: een bewerking is geslaagd. Een bericht als JokesChangedMessage vraagt de ontvanger niet om de grap nog eens te bewaren. De repository blijft de bron van gegevens.

De afzender kent de concrete ontvangers niet meer. Afzender en ontvangers delen wel het berichttype en dezelfde messenger. We maken afhankelijkheden kleiner en explicieter; we laten ze niet verdwijnen.

Messaging heeft ook een prijs: aan een methodeaanroep zie je niet meer onmiddellijk welke ontvangers zullen reageren. Registraties en breakpoints worden belangrijk om de uitvoeringsstroom te volgen. Voor één overzicht dat alleen bij terugkeer moet vernieuwen, kan OnAppearing eenvoudiger blijven.

Gebruik niet voor iedere methodeaanroep een bericht. Voor een gerichte vraag om een bewerking uit te voeren gebruiken we nog steeds het servicecontract. Ons wijzigingsbericht meldt pas ná succes wat gebeurd is.

Een klein bericht en een geïnjecteerde messenger

Pas voor dit onderdeel installeren we het NuGet-package CommunityToolkit.Mvvm. We gebruiken er alleen IMessenger en WeakReferenceMessenger van. De commands blijven de ingebouwde MAUI-Command; daarvoor is dit package niet nodig.

Messages/JokesChangedMessage.cs
namespace JokeApp.Messages;

public class JokesChangedMessage
{
    public Guid JokeId { get; }

    public JokesChangedMessage(Guid jokeId)
    {
        JokeId = jokeId;
    }
}

Het bericht bevat een id, geen control, pagina of wijzigbaar formulierobject. De ontvanger kan de relevante gegevens opnieuw bij de service opvragen.

Voeg using CommunityToolkit.Mvvm.Messaging; toe aan MauiProgram.cs en registreer één gedeelde messenger:

builder.Services.AddSingleton<IMessenger, WeakReferenceMessenger>();

Waarom een singleton? Registraties horen bij een messenger-instantie. Als de lijst zich bij instantie A registreert en de service via instantie B verzendt, ontvangt de lijst dat bericht niet. Binnen deze app moeten de afzender en beide ontvangers dus dezelfde instantie delen.

We gebruiken geen verborgen WeakReferenceMessenger.Default in onze klassen. Constructor injection maakt die gedeelde afhankelijkheid zichtbaar en laat een test een eigen messenger gebruiken. Register betekent straks: dit object wil reageren op dit berichttype. Send laat dezelfde messenger de geregistreerde ontvangers aanroepen.

Alleen na een geslaagde opslag publiceren

Waarom laat de service het bericht versturen? Hier komen de toepassingsregels en de opslagbewerking samen. De service kan na het bewaren vaststellen dat de gevraagde bewerking geslaagd is, ongeacht of de vraag uit het toevoegscherm, het detailscherm of later een import komt.

Als iedere pagina zelf publiceert, moet iedere nieuwe invoerroute dat opnieuw correct doen. We kiezen evenmin voor de repository: die bewaart gegevens, maar organiseert hier niet de communicatie over onze toepassingsbewerkingen. De service is in dit ontwerp de plaats die het geslaagde resultaat meldt.

Voorspel vóór je de code leest: mag een geweigerde dubbele tekst een bericht veroorzaken? En wat als het bewaren mislukt? Zoek straks in elke methode waarom Send dan niet bereikt wordt.

Vervang JokeService door deze versie. De bestaande regels en resultaten blijven behouden; bij iedere geslaagde mutatie komt één bericht.

Services/JokeService.cs
using CommunityToolkit.Mvvm.Messaging;
using JokeApp.Messages;
using JokeApp.Models;
using JokeApp.Repositories;
using JokeApp.Validation;

namespace JokeApp.Services;

public sealed class JokeService : IJokeService
{
    private readonly IJokeRepository _jokeRepository;
    private readonly IMessenger _messenger;

    public JokeService(IJokeRepository jokeRepository, IMessenger messenger)
    {
        _jokeRepository = jokeRepository;
        _messenger = messenger;
    }

    public IReadOnlyList<Joke> GetAll() => _jokeRepository.GetAll();

    public IReadOnlyList<Joke> Search(string? searchText)
    {
        var query = searchText?.Trim() ?? string.Empty;
        return _jokeRepository.GetAll()
            .Where(joke => joke.Text.Contains(
                query, StringComparison.OrdinalIgnoreCase))
            .ToList();
    }

    public Joke? GetById(Guid id) => _jokeRepository.GetById(id);

    public ValidationResult Add(Joke joke)
    {
        ArgumentNullException.ThrowIfNull(joke);

        var duplicateExists = _jokeRepository.GetAll().Any(existing =>
            string.Equals(existing.Text, joke.Text,
                StringComparison.OrdinalIgnoreCase));

        if (duplicateExists)
            return ValidationResult.Failure("Deze grap bestaat al.");

        _jokeRepository.Add(joke);
        _messenger.Send(new JokesChangedMessage(joke.Id));
        return ValidationResult.Success();
    }

    public ValidationResult Update(Guid id, string text, JokeCategory category)
    {
        var existingJoke = _jokeRepository.GetById(id);

        if (existingJoke is null)
            return ValidationResult.Failure("Deze grap bestaat niet meer.");

        var validation = JokeTextValidator.Validate(text);

        if (!validation.IsValid)
            return validation;

        var normalizedText = text.Trim();
        var duplicateExists = _jokeRepository.GetAll().Any(other =>
            other.Id != id &&
            string.Equals(other.Text, normalizedText,
                StringComparison.OrdinalIgnoreCase));

        if (duplicateExists)
            return ValidationResult.Failure("Deze grap bestaat al.");

        var updatedJoke = new Joke(normalizedText, category)
        {
            Id = existingJoke.Id
        };

        if (!_jokeRepository.Update(updatedJoke))
            return ValidationResult.Failure("Deze grap bestaat niet meer.");

        _messenger.Send(new JokesChangedMessage(id));
        return ValidationResult.Success();
    }

    public ValidationResult Remove(Guid id)
    {
        if (!_jokeRepository.Remove(id))
            return ValidationResult.Failure("Deze grap bestaat niet meer.");

        _messenger.Send(new JokesChangedMessage(id));
        return ValidationResult.Success();
    }
}

Een validatiefout verstuurt geen bericht. Gooit de opslag een exception, dan wordt de Send erna evenmin uitgevoerd. Dat maakt verwachte validatiefouten en technische opslagproblemen niet hetzelfde: de eerste zijn resultaten, de tweede vragen in een productieapp een afzonderlijke foutafhandeling.

Werk servicetests bij door een eigen new WeakReferenceMessenger() mee te geven. De DI-registratie van JokeService hoeft niet te veranderen: de container kan de extra dependency nu invullen.

Het overzicht ontvangt de wijziging

Hieronder staat de gezamenlijke versie van JokeListViewModel, inclusief verwijderen en statusfeedback uit de thuisopdracht. Ze laadt eenmaal bij het maken en daarna bij een bericht of expliciete zoekactie.

ViewModels/JokeListViewModel.cs
using System.Collections.ObjectModel;
using System.Windows.Input;
using CommunityToolkit.Mvvm.Messaging;
using JokeApp.Messages;
using JokeApp.Models;
using JokeApp.Navigation;
using JokeApp.Services;

namespace JokeApp.ViewModels;

public sealed class JokeListViewModel : ViewModelBase
{
    private readonly IJokeService _jokeService;
    private readonly INavigationService _navigationService;
    private string _searchText = string.Empty;
    private string _appliedSearchText = string.Empty;
    private string _countText = string.Empty;
    private string _statusMessage = string.Empty;
    private Joke? _selectedJoke;

    public ObservableCollection<Joke> Jokes { get; } = new();

    public string SearchText
    {
        get => _searchText;
        set => SetProperty(ref _searchText, value);
    }

    public string CountText
    {
        get => _countText;
        private set => SetProperty(ref _countText, value);
    }

    public string StatusMessage
    {
        get => _statusMessage;
        private set => SetProperty(ref _statusMessage, value);
    }

    public Joke? SelectedJoke
    {
        get => _selectedJoke;
        set
        {
            if (SetProperty(ref _selectedJoke, value))
            {
                OnPropertyChanged(nameof(SelectedJokeText));
                OpenDetailsCommand.ChangeCanExecute();
                DeleteJokeCommand.ChangeCanExecute();
            }
        }
    }

    public string SelectedJokeText =>
        SelectedJoke?.Text ?? "Selecteer een grap.";

    public ICommand SearchCommand { get; }
    public ICommand ShowAllCommand { get; }
    public ICommand AddJokeCommand { get; }
    public Command OpenDetailsCommand { get; }
    public Command DeleteJokeCommand { get; }

    public JokeListViewModel(
        IJokeService jokeService,
        INavigationService navigationService,
        IMessenger messenger)
    {
        _jokeService = jokeService;
        _navigationService = navigationService;
        SearchCommand = new Command(ApplySearch);
        ShowAllCommand = new Command(ShowAll);
        AddJokeCommand = new Command(
            async () => await navigationService.ShowAddJokeAsync());
        OpenDetailsCommand = new Command(
            async () => await OpenDetailsAsync(), () => SelectedJoke is not null);
        DeleteJokeCommand = new Command(
            DeleteSelectedJoke, () => SelectedJoke is not null);

        messenger.Register<JokeListViewModel, JokesChangedMessage>(
            this, static (recipient, message) => recipient.Receive(message));

        Reload();
    }

    private void Receive(JokesChangedMessage message)
    {
        Reload();
        StatusMessage = "De grappenverzameling is bijgewerkt.";
    }

    public void Reload()
    {
        var matchingJokes = _jokeService.Search(_appliedSearchText);
        SelectedJoke = null;
        Jokes.Clear();

        foreach (var joke in matchingJokes)
            Jokes.Add(joke);

        CountText = $"{Jokes.Count} van {_jokeService.GetAll().Count} grappen";
    }

    private void ApplySearch()
    {
        _appliedSearchText = SearchText.Trim();
        StatusMessage = string.Empty;
        Reload();
    }

    private void ShowAll()
    {
        SearchText = string.Empty;
        _appliedSearchText = string.Empty;
        StatusMessage = string.Empty;
        Reload();
    }

    private async Task OpenDetailsAsync()
    {
        if (SelectedJoke is not null)
            await _navigationService.ShowJokeDetailAsync(SelectedJoke.Id);
    }

    private void DeleteSelectedJoke()
    {
        if (SelectedJoke is null)
            return;

        var result = _jokeService.Remove(SelectedJoke.Id);

        if (!result.IsValid)
            StatusMessage = result.ErrorMessage;
    }
}

Bij verwijderen vernieuwt de succesmelding van de service de lijst via Receive. We roepen niet daarnaast nogmaals Reload aan in het verwijdercommand.

Waarom opnieuw de zoekopdracht uitvoeren en niet zomaar een rij toevoegen of verwijderen? Een bewerkte grap kan wel of niet meer aan de actieve filter voldoen. De teller en selectie moeten ook kloppen. Voor deze kleine verzameling is één gerichte herlaadactie eenvoudiger dan alle gevallen afzonderlijk bijhouden.

De parameter message bevat de gewijzigde id. Deze ontvanger heeft voor het opnieuw laden geen afzonderlijk object nodig; een andere ontvanger kan die id wel gebruiken. Messaging verplicht ons niet tot ingewikkelde incrementele updates.

Een tweede ontvanger: aantallen per categorie

We bouwen nu het statistiekpaneel dat de aanleiding was voor onze ontwerpkeuze. Het telt altijd de volledige bibliotheek, ook wanneer de lijst gefilterd is.

Voor drie tellers op dezelfde pagina is een apart ViewModel niet verplicht. We kiezen er hier bewust voor om een tweede, zelfstandige presentatie te maken: haar telling hangt niet af van de zoektoestand van het overzicht. Daardoor kunnen we ook onderzoeken of een tweede ontvanger kan reageren zonder de eerste aan te passen.

Dit paneel krijgt een eigen ViewModel. Het ontvangt dezelfde IJokeService-abstractie en dezelfde gedeelde messenger, maar kent JokeListViewModel niet. De lijst hoeft het paneel dus niet na iedere bewerking zelf te verversen.

using CommunityToolkit.Mvvm.Messaging;

{

    private int _dadJokeCount;
    private int _otherCount;

    public int ProgrammingCount
    {
        get => _programmingCount;
        private set => SetProperty(ref _programmingCount, value);
    }

    public int DadJokeCount
    {
        get => _dadJokeCount;
        private set => SetProperty(ref _dadJokeCount, value);
    }

    public int OtherCount
    {
        get => _otherCount;
        private set => SetProperty(ref _otherCount, value);
    }

    public JokeStatisticsViewModel(
        IJokeService jokeService,
        IMessenger messenger)
    {
        _jokeService = jokeService;

        messenger.Register<JokeStatisticsViewModel, JokesChangedMessage>(
            this, static (recipient, message) => recipient.Receive(message));

        Reload();
    }

    private void Receive(JokesChangedMessage message)
    {
        Reload();
    }

    private void Reload()
    {
        var jokes = _jokeService.GetAll();
        ProgrammingCount = jokes.Count(
            joke => joke.Category == JokeCategory.Programming);
        DadJokeCount = jokes.Count(
            joke => joke.Category == JokeCategory.DadJoke);
        OtherCount = jokes.Count(
            joke => joke.Category == JokeCategory.Other);
    }
}

Reload leest de volledige verzameling eenmaal en berekent de drie aantallen. Dit is presentatietoestand voor het paneel; er komen geen nieuwe validatieregels of een extra opslagplaats bij.

Registreer dit ViewModel in MauiProgram vóór Build():

builder.Services.AddTransient<JokeStatisticsViewModel>();

De pagina ontvangt straks zowel JokeListViewModel als JokeStatisticsViewModel. Beide ViewModels worden bij het maken eenmaal geladen. Daarna reageren ze onafhankelijk op hetzelfde bericht.

JokeService bewaart een wijziging
└── IMessenger verstuurt JokesChangedMessage
    ├── JokeListViewModel → resultaten van de toegepaste zoekopdracht
    └── JokeStatisticsViewModel → aantallen in de volledige bibliotheek

De service kent geen van beide ontvangers. Er is ook geen aanroep van het ene ViewModel naar het andere. De volgorde waarin ze een bericht ontvangen, mag geen invloed hebben op het resultaat.

Levensduur en thread

WeakReferenceMessenger bewaart ontvangers via zwakke referenties. De registratie alleen houdt een verder ongebruikt ViewModel daardoor niet in leven. De statische callback gebruikt de doorgegeven recipient in plaats van this vast te houden in een closure.

Dat bepaalt niet automatisch wanneer een scherm berichten hoort te verwerken. Ons overzicht en het statistiekpaneel blijven bewust luisteren terwijl een detailpagina erboven staat. Wil je een ontvanger tijdelijk uitschakelen, meld hem dan expliciet af met Unregister of gebruik een passende activatieaanpak. Registreer niet bij ieder verschijnen opnieuw zonder bijbehorend afmelden.

Berichten zijn geen automatische UI-thread-dispatcher. In de kernversie komen de mutaties uit UI-commands en gebruiken we geen achtergrondtaken. Voeg je later achtergrondwerk toe, dan moeten wijzigingen aan gebonden collecties naar de UI-thread worden gebracht.

Zie Microsoft: messenger voor registratie, afmelding en het onderscheid tussen sterke en zwakke referenties.

Samen onderzoeken: één bericht, twee reacties

We gaan de werking niet alleen bekijken wanneer alles toevallig goed lijkt te gaan. Voorspel eerst welke gegevens, rijen en tellers veranderen en controleer daarna de uitvoering.

Het vertrekpunt vastleggen

  1. Voeg een unieke grap toe in Programming, bijvoorbeeld: Deze programmeur bewaart zijn koffie in een variabele.

  2. Zoek op koffie en noteer het aantal resultaten en de drie categorie-aantallen. De statistieken tellen ook de grappen die niet in de resultaten staan.

  3. Plaats breakpoints bij _jokeRepository.Update(updatedJoke), bij de Send onmiddellijk erna en in Receive van beide ViewModels.

  4. Open de grap, verander haar tekst in Een woordgrap over thee zet iedereen aan het denken. en kies Other. Klik nog niet op Opslaan.

Wat verwacht je? Tot nu toe zijn alleen de formulierproperties gewijzigd. De opgeslagen grap, zoekresultaten en statistieken moeten nog dezelfde zijn.

Eén opslagpoging volgen

Klik op Opslaan en stap door de code.

  1. De service controleert de invoer en maakt het vervangende model met dezelfde id.

  2. De repository bewaart de wijziging.

  3. Pas daarna verstuurt de service één bericht met die id.

  4. De twee ontvangers lezen elk de gegevens die zij nodig hebben opnieuw in.

De grap verdwijnt uit de resultaten voor koffie. Ze is niet verwijderd: het totale aantal blijft gelijk. In het statistiekpaneel daalt Programming met één en stijgt Other met één.

Eén verstuurd bericht veroorzaakt hier twee callbacks: één per ontvanger. Dat is geen dubbele verzending. De ontvangers gebruiken niet elkaars resultaat; hun ontvangstvolgorde mag het eindresultaat niet bepalen. Onafhankelijk betekent hier niet dat we ze parallel uitvoeren.

Waarom pas na de opslag?

Bekijk de twee regels voor bewaren en verzenden opnieuw. Wat zou er gebeuren als Send vóór Update stond? De ontvangers zouden opnieuw laden terwijl de oude gegevens nog in de repository staan. Een bericht vóór de controles zou bovendien een geslaagde wijziging suggereren die mogelijk helemaal niet wordt toegestaan.

Je kan de onafhankelijkheid ook aantonen door tijdelijk alleen de messengerregistratie van JokeStatisticsViewModel weg te laten en de app opnieuw te starten. Na een wijziging werkt de lijst nog bij, maar het paneel blijft op zijn beginwaarden staan. Herstel daarna de registratie en start opnieuw. Aan JokeService en JokeListViewModel hoef je niets te veranderen.

Voer de belangrijkste controles ook met de andere repository uit. Het berichtencontract blijft gelijk; alleen het bewaren over een herstart heen verschilt.

Het detailscherm roept nergens MainPage.RefreshJokes aan. De pagina verbindt de twee ViewModels met hun eigen UI, de service publiceert een gebeurtenis en iedere ontvanger bepaalt zelf wat die voor zijn presentatie betekent.

Facultatieve preview - Online grappen via WebAPI

Onze JokeApp kan nu grappen toevoegen, bewerken en bewaren. Als logisch sluitstuk laten we ook een externe bron nieuwe grappen aanleveren. De bestaande service, repository en berichtontvangers blijven hun werk doen.

WebAPI wordt uitgebreider behandeld in andere lessen. Deze preview is volledig uitgewerkt, maar behoort niet tot de verplichte leerstof en wordt alleen klassikaal behandeld als er tijd voor is. Je kan ze ook zelfstandig volgen. We concentreren ons hier op het aansluiten van een bron en het onderscheid tussen een DTO en ons model.

We veronderstellen in dit voorbeeld een geslaagde HTTP-aanroep. Laadindicatoren, netwerkfouten en verdere asynchrone afhandeling horen bij de andere lessen. Neem Task, async en await hier over als hetzelfde vaste recept dat we voor navigatie gebruiken.

Het antwoord van de externe bron bekijken

We gebruiken JokeAPI. Het verzoek naar https://v2.jokeapi.dev/joke/Any?safe-mode&type=single vraagt één grap. Any laat de categorie vrij; type=single vraagt één tekst in plaats van een vraag en antwoord in aparte velden. safe-mode beperkt de aangeboden inhoud, maar blijft geen garantie dat elke grap geschikt is voor de klas.

Een vereenvoudigd antwoord ziet er zo uit. De tekst en id hieronder zijn illustratief, geen werkelijk opgehaalde grap.

{
  "error": false,
  "category": "Programming",
  "type": "single",
  "joke": "Deze programmeur bewaart zijn koffie in een variabele.",
  "id": 123,
  "safe": true,
  "lang": "en"
}

Dit is JSON: gegevens met veldnamen en waarden, geen C#-object. Vergelijk het antwoord met Joke:

  • De tekst staat in joke, terwijl onze property Text heet.

  • De externe id is een getal; onze Id is een Guid voor onze eigen bibliotheek.

  • De externe categorie is tekst en volgt niet noodzakelijk onze JokeCategory-enum.

  • De bron levert ook gegevens die onze app momenteel niet gebruikt, zoals taal en type.

Een extern gegevensformaat hoeft dus niet overeen te komen met het model dat voor onze app het beste past.

Een DTO beschrijft de overdracht

DTO staat voor Data Transfer Object: een object dat gegevens voor de overdracht tussen onderdelen of systemen beschrijft. Hier gebruiken we het om het externe JSON-antwoord in C# te kunnen lezen.

Maak een apart bestand:

Providers/JokeResponse.cs
using System.Text.Json.Serialization;

namespace JokeApp.Providers;

public sealed class JokeResponse
{
    [JsonPropertyName("id")]
    public int ExternalId { get; init; }

    [JsonPropertyName("joke")]
    public string? Text { get; init; }

    [JsonPropertyName("category")]
    public string? Category { get; init; }
}

JsonPropertyName koppelt de naam in JSON aan de C#-property. Zo wordt "joke" gelezen in Text en "id" in ExternalId. We kunnen duidelijke C#-namen kiezen zonder te eisen dat de externe dienst haar antwoord verandert. Zie Microsoft: propertynamen bij JSON-serialisatie.

Niet elk extern veld moet een property krijgen. Velden waarvoor dit DTO geen property aanbiedt, worden bij deze standaarddeserialisatie genegeerd. De init-properties kunnen bij het maken door de deserializer ingevuld worden en worden daarna niet door onze code aangepast.

JokeResponse en Joke hebben verschillende verantwoordelijkheden:

DTO: JokeResponse Model: Joke

Beschrijft gegevens van een externe bron.

Beschrijft een geldige grap in onze applicatie.

Volgt het formaat en de betekenis van de externe velden.

Volgt onze eigen identiteit, categorieën en tekstregels.

Kan nog ontbrekende of voor onze app onbruikbare tekst bevatten.

Bewaakt zijn tekstregels, ook wanneer een andere aanroeper het model gebruikt.

Wordt hier gebruikt bij het inlezen van het antwoord.

Wordt via de bestaande repository bewaard.

Voeg dus geen JSON-attributen aan Joke toe alleen om dit antwoord passend te maken. Wanneer de bron haar veldnamen wijzigt, willen we de aansluiting kunnen aanpassen zonder alle schermen en ons model te wijzigen. Dit is opnieuw Protected Variations.

Bekijk met een breakpoint een ingelezen DTO. Wijs aan waar de externe id en tekst staan. Leg vervolgens uit waarom ExternalId = 123 niet betekent dat we de id van een bestaande lokale grap mogen overschrijven.

Een provider haalt de tekst op

Een provider haalt een suggestie op; een repository bewaart de grappen van onze app. We vervangen LiteDB dus niet door een WebAPI-repository.

Providers/IRandomJokeProvider.cs
namespace JokeApp.Providers;

public interface IRandomJokeProvider
{
    Task<string?> GetTextAsync();
}
Providers/JokeApiProvider.cs
using System.Net.Http.Json;

namespace JokeApp.Providers;

public sealed class JokeApiProvider : IRandomJokeProvider
{
    private readonly HttpClient _httpClient;

    public JokeApiProvider(HttpClient httpClient)
    {
        _httpClient = httpClient;
    }

    public async Task<string?> GetTextAsync()
    {
        var response = await _httpClient.GetFromJsonAsync<JokeResponse>(
            "joke/Any?safe-mode&type=single");

        return response?.Text;
    }
}

GetFromJsonAsync<JokeResponse> vraagt het antwoord op en laat de JSON omzetten naar ons DTO. De provider geeft voor deze eerste import alleen de tekst door. De service hoeft het externe antwoordformaat dus niet te kennen.

We lezen ExternalId en Category in het DTO om het verschil met ons model zichtbaar te maken. De eerste import gebruikt ze nog niet: elke geïmporteerde grap krijgt een nieuwe lokale id en voorlopig de lokale categorie Other. De externe categorieën hoeven we niet aan onze enum toe te voegen.

Voeg using JokeApp.Providers; toe aan MauiProgram en registreer vóór Build():

builder.Services.AddSingleton(_ => new HttpClient
{
    BaseAddress = new Uri("https://v2.jokeapi.dev/")
});
builder.Services.AddTransient<IRandomJokeProvider, JokeApiProvider>();

We hergebruiken één client. De provider bevat de kennis van het verzoek; het ViewModel krijgt geen URL of HttpClient.

De bestaande service blijft het toevoegen bewaken

Voeg aan IJokeService toe:

Task<ValidationResult> ImportRandomAsync();

Voeg using JokeApp.Providers; en dit veld toe aan JokeService:

private readonly IRandomJokeProvider _randomJokeProvider;

Vervang de constructor door:

public JokeService(
    IJokeRepository jokeRepository,
    IMessenger messenger,
    IRandomJokeProvider randomJokeProvider)
{
    _jokeRepository = jokeRepository;
    _messenger = messenger;
    _randomJokeProvider = randomJokeProvider;
}

Voeg vervolgens de importmethode toe. Behoud alle bestaande methoden voor zoeken, toevoegen, bewerken en verwijderen.

public async Task<ValidationResult> ImportRandomAsync()
{
    var text = await _randomJokeProvider.GetTextAsync();
    var validation = JokeTextValidator.Validate(text);

    if (!validation.IsValid)
        return ValidationResult.Failure(
            $"De opgehaalde grap past niet bij onze tekstregels: {validation.ErrorMessage}");

    return Add(new Joke(text!, JokeCategory.Other));
}

We hergebruiken hier de validatie uit onze eigen app; we bouwen geen nieuw hoofdstuk over WebAPI-foutafhandeling. Ook tekst van een externe bron moet aan onze modelregels voldoen voordat we een Joke maken.

text! vertelt de compiler dat de succesvolle validatie een ontbrekende tekst uitsluit. Dat teken voert zelf geen runtimecontrole uit.

Daarna doet Add precies wat het al deed: controleren op dubbele tekst, bewaren en na succes een bericht versturen. Zowel de lijst als het statistiekpaneel reageren vanzelf. Bij een duplicaat geven we het mislukte resultaat door in plaats van toch succes te melden.

De importknop aansluiten

Voeg aan JokeListViewModel de commandproperty toe:

public ICommand ImportJokeCommand { get; }

Initialiseer ze in de bestaande constructor:

ImportJokeCommand = new Command(async () => await ImportAsync());

Voeg de methode toe:

private async Task ImportAsync()
{
    var result = await _jokeService.ImportRandomAsync();
    StatusMessage = result.IsValid
        ? "Een nieuwe grap is toegevoegd."
        : result.ErrorMessage;
}

De bestaande statusmelding toont het resultaat van de import. We voegen geen laadstatus of afzonderlijke netwerkafhandeling toe.

Voeg in MainPage.xaml een laatste Auto-rij aan de hoofd-Grid toe. Na het statistiekpaneel en de actiebalk heeft die rij index 6. Plaats daarin:

<Button Grid.Row="6" Text="Online grap ophalen"
        Command="{Binding ImportJokeCommand}" />

Het sluitstuk uitproberen

  1. Start met een werkende internetverbinding en klik op Online grap ophalen.

  2. Kijk met een breakpoint naar JokeResponse en volg de tekst naar de service.

  3. Controleer na een geslaagde toevoeging de lijst en het statistiekpaneel. Met een actieve zoekopdracht hoeft de nieuwe grap niet in de resultaten te verschijnen.

  4. Open de geïmporteerde grap en wijzig haar categorie. De bestaande bewerkstroom werkt ook voor online grappen.

  5. Herstart de app: de grap is in dezelfde lokale database bewaard als de handmatig ingevoerde grappen.

De verschillende bronnen veranderen niets aan de rest van de app. Een gebruiker voert tekst in via het formulier of een provider haalt tekst op; vanaf de service volgen beide dezelfde regels en dezelfde opslag- en berichtenstroom.

Thuisopdracht - Werk de bewerkervaring af

Deze opdracht gebruikt alleen de kern van de les; WebAPI is niet verplicht. Je werkt verder in dezelfde JokeApp en levert geen tweede demonstratieproject op.

Must

  • Behoud de werkende stroom overzicht → details → opslaan of annuleren, met dezelfde id en gedeelde validatieregels.

  • Voeg HasChanges toe aan JokeDetailViewModel. Bewaar bij het laden de oorspronkelijke tekst en categorie; vergelijk daarmee de huidige formulierwaarden.

  • Toon met binding een melding Niet-opgeslagen wijzigingen wanneer HasChanges waar is. Werk die afgeleide property bij na een tekst- of categoriewijziging.

  • Voeg een command Herstellen toe dat de oorspronkelijke formulierwaarden terugzet, zonder iets naar de repository te schrijven. Het command is alleen beschikbaar wanneer er wijzigingen zijn.

  • Behoud validatie bij Opslaan. HasChanges is feedback over verschillen, geen bewijs dat de invoer geldig is.

  • Bewijs dat alleen geslaagde toevoegingen, wijzigingen en verwijderingen een JokesChangedMessage versturen.

  • Licht je ontwerp kort toe aan de hand van je eigen code:

    • Waarom schrijft Herstellen niets naar de repository?

    • Waarom betekent HasChanges niet dat de invoer geldig is?

    • Stel dat een derde onderdeel moet reageren op gewijzigde grappen. Waar voeg je code toe, en waarom hoef je de afzender daarvoor niet aan te passen?

Should

  • Vraag via een apart dialoogcontract bevestiging wanneer de gebruiker met Annuleren niet-opgeslagen wijzigingen zou weggooien. De gewone terugknop valt niet automatisch onder dat command; onderschep die alleen als afzonderlijke uitbreiding.

  • Behoud een bevestiging vóór definitief verwijderen en controleer het detailscherm op een smal venster.

Could

  • Schrijf tests die ook na een geweigerde wijziging de oorspronkelijke tekst en id controleren.

Facultatieve uitbreiding - Kies de online categorie

Deze uitbreiding hoort bij de WebAPI-preview. Ze is geen verplicht onderdeel van de opdracht. Vertrek van de werkende importknop en laat de gebruiker bepalen uit welke online categorie een grap wordt opgehaald.

  • Maak een aparte OnlineJokeCategory-enum in Providers met All, Programming, Wordplay en Miscellaneous. Dit zijn keuzes voor de bron, geen extra waarden voor de lokale JokeCategory.

  • Toon de keuzes via een gebonden Picker in het overzicht en selecteer standaard All. Haal nog niets op wanneer de selectie verandert; dat gebeurt pas via de importknop.

  • Geef de gekozen waarde vanuit het ViewModel via ImportRandomAsync(OnlineJokeCategory category) door aan GetTextAsync(OnlineJokeCategory category) van de provider. Werk beide interfaces en implementaties samen bij.

  • Vertaal uitsluitend in JokeApiProvider de keuzes naar de namen uit de API-documentatie: All → Any, Programming → Programming, Wordplay → Pun en Miscellaneous → Misc.

  • Bouw in de provider het pad joke/{categoryName}?safe-mode&type=single op. Behoud de filters uit het voorbeeld. De pagina en het ViewModel bouwen geen URL.

  • Voor deze oefening blijft de lokale opslagcategorie Other, zoals in de preview. De online keuze filtert de bron; een lokale categorie toekennen is een afzonderlijke beslissing. Gebruik dus niet zomaar Enum.Parse<JokeCategory> op de externe categorienaam.

Een switch-expressie in de provider kan de vier online keuzes naar API-namen vertalen. De bindings en de beginselectie volgen hetzelfde patroon als de categoriepicker op het toevoegscherm.

Controleer met een breakpoint welk verzoek de provider maakt. Bij Programming moet het DTO een programmeergrap beschrijven; bij Wordplay heet de categorie in het antwoord Pun. De service ontvangt nog steeds alleen de tekst van de provider. Na een geslaagde import werken opslag, lijst en categorietellers zonder extra aanroepen vanuit de pagina.

Leg ten slotte uit waarom het DTO, de online filterkeuze en JokeCategory drie verschillende rollen hebben.

Eindcontrole van de reeks

Loop de app door als gebruiker: toevoegen, zoeken, details openen, bewerken, herstellen, annuleren, verwijderen en herstarten. Controleer ook lege invoer, dubbele tekst, geen selectie en een onbekende id.

Leg bij één handeling uit welke verantwoordelijkheid in de View, het ViewModel, de service, het model en de repository zit. Toon waar DI de objecten samenstelt, waarom een wijzigingsbericht pas na succesvolle opslag wordt verstuurd en hoe beide ontvangers er onafhankelijk op reageren.
